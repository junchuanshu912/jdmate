30 秒看懂业务逻辑

求职最费时间的不是「不会写」，而是同一个动作要重复几百遍：一个岗位几十条要求， 我真正对得上的常只有三四条；招聘者每天要看成百条「您好，我对这个岗位很感兴趣」； 而能证明我的东西——量化成果、项目细节、技术选型的理由——全埋在简历里，根本没时间一条条挑出来对应。

1
触发
我在 Boss 直聘点开一个岗位 —— 这是整个流程唯一需要我发起的动作
2
读懂岗位
抽出职责 / 要求 / 加分项 / 关键词。抽取质量可查：面板里能展开它读到的原文
3
对照自己
简历结构化后与 JD 求交集：命中什么、缺什么 —— 缺口比亮点更值得知道
4
生成 + 打分
写 1~5 条开场白，本地打分并给出理由；话术里每个数字都回查简历
5
人做最后一步
我把选中的填进输入框，回车自己按 —— 产品负责写到我敢发，不替我决定发不发
≤ 3 秒

0 编造

需求是怎么一步一步收敛的

这是我认为比界面更值得看的部分：下面 8 条都是真实发生过的判断，写清楚了最初想要什么、为什么改、最后怎么做。

最初的想法为什么改最后怎么做
让 AI 全自动打招呼，省到底 自动发送会让我在完全不知情时说出一堆不像我的话，还可能触发平台风控 砍掉发送——不是默认关闭，是根本不存在这个开关
所有环节都上大模型 打分要可解释、护栏必须可信、「拿到页面真实文本」模型做不到 全项目只有 2 处调 LLM，其余规则化（详见下方折叠区）
做一版墨刀可编辑原型交付给 HR 墨刀「HTML 转原型」不执行 JS：下拉点不开、按钮没反馈，跳转还得手工配热区 改成 GitHub Pages 真网页——交互全活，一个链接发给谁都能看
演示页加一排「状态切换」方便看 那是写代码的人的调试便利；对观众等于「这些画面是我摆好的」 删掉，每个状态必须由真实操作走到（点生成 / 关权限 / 删简历…）
设置项做得越全越好 全摆出来的结果是「不知道该填哪些」，注意力被稀释 两步引导 + 渐进式披露：折叠而不是删除，功能一个不少
简历入口支持拖拽 + 读文件夹 + 粘贴 三个入口就是三份维护成本，而我自己用只需要最省事的那条 留拖拽 / 读文件夹，粘贴只作为识别失败时的兜底
简介里写上「1 万行代码 / 175 个测试」 看我作品的人不关心这个；自夸占了位置，反而挤掉真正该说的 整块删掉，换成业务逻辑与决策记录
需求聊个大概就开工写代码 需求没对齐就动手，返工成本最高 先出计划 / 原型 / 需求文档，确认无误才开始开发

四个想清楚了的取舍

这些是做完之后回头看，最影响成品质量的决定。

不无脑用 AI：模型只负责「理解语义」

抽取、分段、打分、护栏全部先用确定性规则算，只有「规则给不出结构化字段」时才调 LLM； 模型超过 12 秒就用规则结果渲染并标注原因。 理由：聊天助手可以等，找工作的工具不能。

不发送，是唯一不可配置的规则

自动打招呼会让我在完全不知情的情况下说出不像我的话，还可能触发平台风控。 所以这个开关我没有做——不是默认关闭，是根本不存在。

数据不出本机

单一扩展、零后端。简历、收藏、生成历史只存在本机 IndexedDB， API Key 经 AES-GCM 加密后落盘。没有账号体系，也没有任何上传。

演示页不做「状态切换器」

右侧栏每个状态都得由真实操作走到：关掉站点权限、删掉简历、把 Base URL 改错、切到 DEMO…… 给外人看的东西，「方便」不能靠外挂开关。

哪里用了模型，哪里故意不用8 个环节 · AI/Agent 分工

这条分工线是刻意画的：模型只出现在「必须理解语义」的地方，其余交给脚本与规则 —— 更快、更省 token、结果可复现，也不会因为模型抽风就把功能弄挂。

环节谁来干为什么这么分
抓页面文本 / 反爬混淆还原 脚本 · 不用模型 「拿到用户真正看到的文本」是模型做不到的事 —— 它只能看见我们喂给它的东西。
JD 结构化（职责 / 要求 / 加分项 / 关键词） LLM Agent 节点 「从杂乱文本里读出结构」正是大模型最擅长的事。但它有门禁： 标题、公司、职责 ≥3、要求 ≥3、关键词 ≥6 时规则直接给结果，根本不调模型。
简历结构化（经历 / 技能 / 量化成果 / 年限） 脚本规则 · 不用模型 简历格式相对固定，规则更稳、不花 token、每次结果一致 —— 这是可复现性的前提。
「简历 ∩ JD」匹配点 本地集合运算 求交集是确定性计算，本地做又快又准还不花钱，比让模型「自己找找看」可靠得多。
开场白生成 LLM · 主战场 唯一真正需要语言能力的地方：一次生成 1~5 条风格与长度都不同的候选。
候选打分与排序 本地 7 维加权 · 不用模型 可解释、可复现、免费。每条都能说清「为什么推荐它、还差哪几个关键词」—— 让模型给自己打分是没法解释的。
事实护栏（数字回查简历） 脚本规则 · 不用模型 不能让模型自己校验自己。它编出来的数字，必须由简历原文来判。
模型挂了怎么办 规则结果兜底 超时 12 秒 / JSON 非法 / 没配 Key → 静默回退到规则结果并说明原因。 模型是增强项，不是依赖项：它挂了，产品只是变笨一点，不会不可用。

每一次 LLM 调用都长成一个可复用的 Agent 节点： 规则先跑 → 门禁 skipLlmIf → 调模型 → Zod 校验 JSON → 与规则结果合并 → 失败静默回退。 后来要加「简历结构化」这类新能力，只需要再写一个 AgentDefinition （提示词 + 输出 schema + 门禁 + 兜底），不用碰主流程。

六个功能，各自解决上面哪一步功能清单
🔍
JD 抽取：脚本拿到事实，Agent 读懂结构

脚本负责「拿到用户真正看到的文本」：先还原 Boss 的反爬混淆（乱码类名、隐藏误导文本）， 再剔除「相似职位 / 推荐位 / 页脚」这些长得像正文的噪声，四级回退。 然后 LLM Agent 节点把杂乱文本读成职责 / 要求 / 加分项 / 关键词。

🤖
Agent 节点：把模型当成不可靠依赖来设计

每次调用都是同一个骨架：规则先跑 → 门禁 skipLlmIf → 调模型 → Zod 校验 JSON → 与规则结果合并 → 失败静默回退。超时 12 秒、JSON 非法、没配 Key，都退回规则并说明原因。

✍️
LLM 主战场：写开场白，而不是夸岗位

七层提示词（系统约束 / 简历 / JD 原文 / 本地算好的匹配点 / 偏好 / 风格 / 输出契约） 一次生成 1~5 条候选，风格 5 选、长度 4 档。匹配点本地算好再给模型，既省 token 又提高相关性。

📊
打分不用模型：本地 7 维加权

关键词覆盖、长度适配、量化密度、个性化程度、可读性、新鲜度、风格匹配，加权后减去套话扣分。 每条都给分数、理由、命中的关键词、还差哪几个。

🛡️
事实护栏：用规则拦住模型编的数字

话术里每个数字都回查简历原文，简历里没有的会被点名标出。 不能让模型自己校验自己。

🔁
收藏岗位 + 反向优化简历

一键收藏好岗位；攒够一批后反查我反复对不上的是哪几项能力，再回头改简历 —— 投递方向比投递数量值钱。
